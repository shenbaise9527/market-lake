# TB 级行情数据湖的架构决策

> 这份文档给的是**决策**和**理由**，不是教程。每一节都以"你要选什么 + 代价是什么"结尾。

## 1. 分层

```
raw       原始落地，一行不改，永远可重放      t trades / book / orders   按天分区
  ↓
1s / 1m   常用粒度预聚合，省掉 90% 的重复计算  按 (dt, symbol) 聚簇
  ↓
daily     日线 + 复权因子 + 合约元数据         小块，可全量缓存
```

理由：研究端 95% 的查询落在"分钟 bar + 少数合约"上，让它们读几百 KB 而不是几 GB。
**代价**：多一份存储（约 +15%）和一条必须幂等的重算链路。

## 2. 目录与分区

```
lake/data/raw/trades/dt=2026-11-05/exchange=SH/part-0003.parquet
```

- **按天分区**：行情天然按天来，且绝大多数查询带日期。日切也让补数、重跑、过期都变简单。
- **不要按 symbol 分目录**：A 股 5000+ 合约 → 5000+ 目录、几万个小文件，元数据开销会吃掉收益。
- **第二层用桶而非合约**：`bucket = hash(symbol) % 16`，写进文件内的列，靠 `(symbol, ts)` 排序 + 行组统计剪枝来定位。
- **分区键不要重复落列**：`dt` 只在路径里，文件里不再存一列 dt（省 8 字节/行 + 一列的统计开销）。

**代价**：跨多日的大范围查询会打开几百个文件，要把文件数控制在千级以内。

## 3. 文件尺寸与行组

| 参数 | 推荐值 | 依据 |
|---|---|---|
| 单文件大小 | 256MB–1GB | 小于 100MB 元数据开销占比过高；大于 2GB 单文件修复成本高 |
| row group | 128MB 左右（或 100 万行） | 太小 → 统计信息粒度细但每行组开销大；太大 → 剪枝粒度粗 |
| page | 1MB | 默认值通常够；点查密集时可降到 256KB |
| 排序键 | `(symbol, ts)` | 让"单合约时间段"的查询能整块跳过行组 |

一天一个交易所的 tick 常有 2000 万–1 亿行，单文件装不下 → 按桶切 8–16 个文件，每个文件内部仍按 `(symbol, ts)` 排序。

## 4. 写入：幂等与原子

```
1. 写到 lake/_tmp/<job_id>/...
2. fsync
3. 原子 rename 到目标分区（同分区已有同名文件则先删/或带 version 后缀）
4. 更新 _manifest/dt=.../meta.json（行数、时间范围、源文件 checksum）
```

- **重跑必须幂等**：重算某天数据 = 删掉该天分区重写，而不是 append。
- **不要原地修改文件**：Parquet 不可变，任何"改一行"都要重写整个行组。
- **补数**：晚到的 tick 写入对应历史分区（重写该天），而不是塞进"今天"。

**代价**：重写一天 = 读写一整天数据。所以日分区粒度不能太细（小时分区会让补数变贵），也不能太粗（月分区会让单次重写不可接受）。

## 5. 去重与清洗

去重键：`(exchange, symbol, ts, seq, channel)`。`seq` 是交易所序号，`channel` 区分不同行情通道（L1/L2/逐笔）。

清洗规则要显式落成一张表，别写死在代码里：

| 规则 | 处理 |
|---|---|
| 重复行（键相同） | 保留第一条，计数上报 |
| 时间倒序 | 排序修正，计数上报 |
| 序号断档 | 标记 `gap=true`，不插值 |
| 价格跳变 > 5σ | 标记异常，保留原值（回测要能看到脏数据的影响） |
| 集合竞价时段 | 单独标记，不进 bar 聚合 |

**不要静默丢数据**：所有清洗动作都要在质量报告里出现计数，否则出问题无法回溯。

## 6. Compaction

触发条件：单分区内文件数 > 阈值（如 32）或平均文件 < 50MB。
做法：读该分区全部文件 → 按 `(symbol, ts)` 重排 → 写成目标大小的新文件 → 原子切换。

频率：每日低峰跑一次；不要每次写入都合并（放大写放大）。

## 7. 是否需要 Iceberg / Delta

先问三个问题：

1. 有多个写入方吗？（多个采集进程/多台机器并发写同一张表）
2. 需要 upsert 吗？（修正历史数据、覆盖错误分区）
3. 需要时间旅行/快照隔离吗？（回测要"某天的数据版本"）

三个都是"否" → **别上**，纯目录 + Hive 分区 + manifest 就够了，运维成本差一个量级。
任意一个是"是" → 上 Iceberg（生态成熟，DuckDB / Polars / Spark 都认）。

## 8. 容量估算（自己按实际填）

```
每日行数 R × 每行压缩后字节 B × 保留天数 D × 副本数 1（三副本交给对象存储）

示例：A 股 L2 逐笔，3000 合约 × 每日 8 万笔 = 2.4 亿行/日
     压缩后 ~6 字节/行（zstd，按 (symbol,ts) 排序）→ 1.4GB/日 → 350GB/年
     加 1s/1m 派生层 → 约 400GB/年
```

**结论**：单机 NVMe（2–4TB）+ 对象存储冷备，足以支撑一个中型私募的全部行情历史。
不要一开始就上分布式——那是给"每天 10 亿行 + 多人并发写"准备的。

## 9. 并发与算力

| 场景 | 方案 |
|---|---|
| 单人研究 | 本地 DuckDB / Polars，零运维 |
| 3–10 人团队 | 一台大内存机器 + DuckDB 服务模式（读多写少），或 ClickHouse |
| 多人 + 大范围扫描 | Trino / DataFusion 集群，或直接上 Spark（只有真的需要时） |

**代价**：每上一级，运维复杂度翻倍，而行情数据的实际查询模式往往简单到一台机器就够。

## 10. 常见错误清单

- 按 symbol 建目录 → 小文件地狱
- 用 CSV/JSON 做中间落地 → 后来每个环节都在解析文本
- 时间戳存字符串 → 无法做范围剪枝，排序也变慢
- 价格用 double 存分 → 累加出现 0.30000000000000004 类误差，对账对不上
- 每次查询都 `collect()` 全量 → 数据湖退化成内存数据库
- 不记录写入的 `created_by` 和参数 → 三个月后没人知道这批文件怎么来的
