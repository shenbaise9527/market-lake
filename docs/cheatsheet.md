## Parquet 编码（W2 填）

| 列 | 数据特征 | 编码 | 体积 | 相对 PLAIN | 备注 |
|---|---|---|---|---|---|
| `ts` | 严格递增 int64 | RLE_DICTIONARY（pyarrow 默认） | 233 KB / 48k 行 | — | 反面教材，字典对高基数列无效 |
| `ts` | 同上 | DELTA_BINARY_PACKED | （待填） | | 预期体积降到 1/5 |
| `px` | 两位小数 float64 | PLAIN | 60 B/行（全列合计） | 1.0x | 与 zstd 配合最好 |
| `px` | 同上 | BYTE_STREAM_SPLIT | 73 B/行 | 1.22x | **反而变大**，见下 |

**实测反直觉结论**（73,375 行单合约单日，`reports/bench.md` 可复现）：
两位小数的价格是极低基数（几百个不同值），`PLAIN + zstd` 已经压到极致；
`BYTE_STREAM_SPLIT` 会把相同的高位字节摊开、但同时废掉字典与重复模式，**体积反而 +22%**。
BSS 真正有效的场景是：价格精度高（>6 位有效数字）、取值近乎连续、且该列本来就关掉了字典。

## 压缩（W3 填）

| 算法 | 级别 | 体积 | 字节/行 | 全扫耗时 | 适用 |
|---|---|---|---|---|---|
| none | — | 4.41 MB | 60.1 | 2 ms | 热数据、反复扫 |
| snappy | — | 1.40 MB | 19.1 | 2 ms | 折中默认值 |
| zstd | 3 | 0.72 MB | 9.8 | 3 ms | 冷数据首选 |

（实测：73,375 行 trades、`(symbol, ts)` 排序、row_group=262144。压缩比 6.1x，代价是全扫多 1ms。）
`zstd-19` 在 tick 数据上收益通常 <5%、写耗时翻倍，不值得。**先测再开**。

## 排序与剪枝（W3 填）

| 场景 | 排序键 | 体积 | 点查耗时 | 说明 |
|---|---|---|---|---|
| 未排序 | 无 | 0.82 MB | 2.0 ms | 单文件单行组，剪枝无从发挥 |
| 按 `(symbol, ts)` | 是 | 0.72 MB | 2.2 ms | 体积降 12%，延迟未变 |

**为什么这里看不出剪枝收益**：一个文件只有一个行组、只装一个合约时，排不排序都得整块读。
排序的价值要等到「一个文件装多合约、多行组」时才显现——第 3 周的任务 4 会让你造出这种数据，
那时 `Rows Scanned` 的差距才会是 10 倍量级。这是本地实验最容易误判的一点：**数据规模不到，结论就是错的**。

## 踩过的坑（随时加）

| 现象 | 原因 | 解法 | 周 |
|---|---|---|---|
| ASOF JOIN 跑几分钟 | DuckDB 对 `read_parquet + WHERE symbol=...` 的基数估计失真，退化成嵌套循环 | 先物化成临时表再 ASOF（0.02s） | W6 |
| Polars `group_by_dynamic` 报 input data is not sorted | 乱序 tick 未排序 | 先 `.sort(["symbol","t"])` | W7 |
| Polars 过滤 `dt` 报类型错 | hive 分区键被推断为 Date | 用 `pl.date(2026,11,5)` 比较 | W7 |
| 时间戳全部挤在同一秒 | 给纳秒时间戳加偏移时混用了秒单位 | 偏移量 ×1e9 | W1 |
